The Core Problem

The system is built on a sound architecture — gRPC spine, event bus, HTTP API, Qt GUI — but the plumbing between layers is broken in 12 places. Data is produced correctly at the source but silently dropped before it reaches the screen. The most damaging bugs: (1) the server process never gets the spine address so all gRPC events are swallowed at the bridge, (2) a dead gRPC client in the server event-stream widget means spine events never reach the server GUI even if the bridge were fixed, (3) completing a command never triggers a dashboard refresh, (4) the tenant page uses hardcoded fake data and has no API wiring, and (5) the app starts on the wrong page.

B3 — Dead GrpcJobClient in ExecutionEventStreamWidget

Critical · gui/ExecutionEventStreamWidget.h + gui/MainWindow.h

What's broken

ExecutionEventStreamWidget creates its own GrpcJobClient, stores it as m_grpcClient, and connects m_grpcClient->eventReceived to its onSpineEvent slot. The problem: m_grpcClient->submit() is never called. A GrpcJobClient does nothing until submit() is called — that's what starts the gRPC thread and opens the WatchJob stream. So onSpineEvent never receives any event. The real spine events flow through LiveJobWidget's own client, which is a completely separate object. The onSpineEvent handler is beautifully implemented but permanently unreachable.

In MainWindow::buildUi(), the only connection between live and server->eventStream() is notifyJobSubmit(command) — which only updates the command label string, not the events themselves.

Bug — ExecutionEventStreamWidget constructor: client created, signals wired, submit() never called
// ── Spine gRPC watcher ────────────────────────────────── m_grpcClient = new GrpcJobClient(this); m_grpcClient->configure(...); connect(m_grpcClient, &GrpcJobClient::eventReceived, this, &ExecutionEventStreamWidget::onSpineEvent); // ← m_grpcClient->submit() is NEVER called. // No gRPC thread starts. eventReceived never fires. // onSpineEvent is dead code.
Fix — Step 1: Remove dead client from ExecutionEventStreamWidget constructor
// DELETE these lines from the constructor: m_grpcClient = new GrpcJobClient(this); m_grpcClient->configure(...); connect(m_grpcClient, &GrpcJobClient::submitted, ...); connect(m_grpcClient, &GrpcJobClient::eventReceived, ...); connect(m_grpcClient, &GrpcJobClient::failed, ...); // DELETE member: GrpcJobClient *m_grpcClient = nullptr;
Fix — Step 2: Expose accessor on LiveJobWidget
// Add to LiveJobWidget public section: GrpcJobClient *grpcClient() const { return m_client; }
Fix — Step 3: Wire the real client in MainWindow::buildUi()
// After: connect(live, &LiveJobWidget::jobSubmitted, server->eventStream(), // &ExecutionEventStreamWidget::notifyJobSubmit); connect(live->grpcClient(), &GrpcJobClient::eventReceived, server->eventStream(), &ExecutionEventStreamWidget::onSpineEvent);

B5 — TSH_SPINE_CONTROL_ADDR Missing from Server Launch — SpineEventBridge Is Dead

Critical · start.sh + server/Server.cpp + server/SpineEventBridge.h

What's broken — the full chain

In Server.cpp, SpineEventBridge is constructed with tsh::Config::read_string("TSH_SPINE_CONTROL_ADDR", ""). In SpineEventBridge.h, if spine_addr.empty(), the constructor returns immediately and stub_ stays nullptr. In watch_job(): if (!stub_) return; — a silent no-op. B6 — SpineEventBridge Hardcodes InsecureChannelCredentials

High · server/SpineEventBridge.h

What's broken

GrpcJobClient (in the GUI) correctly reads TSH_GRPC_INSECURE_DEV to decide between insecure and TLS credentials. SpineEventBridge — the server-side component that connects the HTTP server to the spine — hardcodes grpc::InsecureChannelCredentials() unconditionally. In any deployment where the spine gRPC server requires TLS (i.e. production), the bridge will silently fail to connect. Combined with B5 (address not set at all in dev), the bridge is broken in every environment.

Bug — SpineEventBridge.h
auto channel = grpc::CreateChannel( spine_addr, grpc::InsecureChannelCredentials()); ← always insecure
Fix — Replace with credential helper
auto channel = grpc::CreateChannel(spine_addr, makeChannelCredentials()); static std::shared_ptr<grpc::ChannelCredentials> makeChannelCredentials() { const char *ins = std::getenv("TSH_GRPC_INSECURE_DEV"); if (ins && std::string(ins) == "1") return grpc::InsecureChannelCredentials(); grpc::SslCredentialsOptions opts; const char *ca = std::getenv("TSH_GRPC_ROOT_CA"); if (ca) { std::ifstream f(ca); opts.pem_root_certs = std::string( std::istreambuf_iterator<char>(f), {}); } return grpc::SslCredentials(opts); }
gRPC Server Bridge silent-fails in any TLS-enabled deployment

B7 — Spine-Path Executions Never Call record_command() — Metrics Always Zero

B9 — GrpcJobClient Has No Reconnect Logic — Stream Dies Silently

High · gui/GrpcJobClient.h

What's broken

GrpcJobClient runs a single thread that calls submit() then streams events via WatchJob. When reader->Read() returns false — either because the job ended, the server closed the stream, or a network interruption — the thread simply exits. No reconnect. No retry. No GUI indicator. The widget appears alive (no error shown) but will receive no further events. If the spine server restarts mid-job, events are silently lost forever.

Bug — GrpcJobClient.h: thread exits when stream closes
auto reader = stub->WatchJob(&watchContext, watch); tinyshell::v1::JobEvent event; while (!m_stop.load() && reader->Read(&event)) { emit eventReceived(event); ... } // ← thread exits here. no retry. no log. no GUI update.
Fix — Add retry loop with exponential backoff
int backoff_ms = 500; while (!m_stop.load()) { try { auto channel = grpc::CreateChannel(...); auto stub = ...; // submit + watch loop while (!m_stop.load() && reader->Read(&event)) { ... } const auto status = reader->Finish(); if (status.ok()) break; // clean completion emit streamDisconnected(); // surface in GUI } catch (...) {} std::this_thread::sleep_for(std::chrono::milliseconds(backoff_ms)); backoff_ms = std::min(backoff_ms * 2, 16000); }
gRPC GUI Events stop silently on any network blip or server restart

B10 — m_lastCommand Is a Race: Overlapping Jobs Get Wrong Command Labels

Medium · gui/ExecutionEventStreamWidget.h

What's broken

ExecutionEventStreamWidget stores a single QString m_lastCommand set by notifyJobSubmit(). When onSpineEvent() adds a row, it uses m_lastCommand for the Command column. If two jobs are submitted before the first completes, m_lastCommand is overwritten to the second job's command. All subsequent events for Job A are labeled with Job B's command name. The table shows incorrect audit data.

Bug — global mutable state shared across concurrent jobs
QString m_lastCommand; // ← single global string, overwritten on each submit void notifyJobSubmit(const QString &command) { m_lastCommand = command; // ← overwrites Job A's name when Job B submits } void onSpineEvent(tinyshell::v1::JobEvent event) { ... addRow(ts, type, job_id, actor, m_lastCommand, state, detail); // ↑ wrong if two jobs overlap }
Fix — Map job_id → command
QHash<QString, QString> m_jobCommands; // job_id → command void notifyJobSubmit(const QString &jobId, const QString &command) { m_jobCommands[jobId] = command; } void onSpineEvent(tinyshell::v1::JobEvent event) { const auto jobId = QString::fromStdString(event.job_id()); const auto cmd = m_jobCommands.value(jobId, "—"); addRow(ts, type, jobId, actor, cmd, state, detail); // Clean up completed jobs: if (isTerminalEvent(event.type())) m_jobCommands.remove(jobId); }

B11 — ClientConnectionPanel and AuditLogPanel Poll Full History Every Second

Medium · gui/ClientConnectionPanel.h + gui/AuditLogPanel.h + gui/JobSchedulerPanel.h

What's broken

ClientConnectionPanel::pollClients() and other secondary panels call m_api->getText("/control/events", ...) without a ?since_sequence=N parameter. Every poll downloads the entire event history (up to the bus cap of 10,000 events), parses it, and rebuilds the table from scratch. ExecutionEventStreamWidget (which works correctly) already has m_lastHttpSeq and uses ?since_sequence=%1. These panels don't. Under load, this becomes O(n) per second and causes visible table flicker from setRowCount(0) + full rebuild.

Bug — ClientConnectionPanel polls entire history

Fix — same pattern already used in ExecutionEventStreamWidget
// 1. Add member: quint64 m_lastSeq = 0; // 2. Use since_sequence in URL: m_api->getText( QString("/control/events?since_sequence=%1").arg(m_lastSeq), [this](QString body, ...) { ... // 3. B12 — .env Contains Literal Placeholder Strings That Bypass Token Guard

Medium · .env

What's broken

The .env file contains export TSH_API_TOKEN=<generate with: ./generate_secrets.sh>. If a user sources this file as-is, TSH_API_TOKEN is set to the literal string <generate with: ./generate_secrets.sh>. The guard in start.sh checks if [[ -z "$API_TOKEN" || "$API_TOKEN" == "dev-token-1234" ]] — neither condition matches a non-empty non-default string. The server launches with a token that is a literal angle-bracket instruction, and every API call with a real token will fail authentication.

Bug — .env
export TSH_API_TOKEN=<generate with: ./generate_secrets.sh> export TSH_ZK_SECRET=<generate with: ./generate_secrets.sh>
Fix — Use empty assignments that the guard catches
# Run: source <(./generate_secrets.sh) before starting export TSH_API_TOKEN= export TSH_ZK_SECRET= export TSH_TLS_CERT=certs/server.crt export TSH_TLS_KEY=certs/server.key
Config Server launches with unusable token; every auth request fails
